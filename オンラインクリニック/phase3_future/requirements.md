# Phase 3：将来内製化要件メモ

作成日：2026-05-20

> Phase 3に進む条件：月間診療件数が一定規模を超え、既存プラットフォームの手数料・制約がボトルネックになり始めたとき。

---

## 内製化を検討する判断基準

| 判断基準 | 目安 |
|---|---|
| 月間診療件数 | 200件以上（プラットフォーム手数料が顕在化） |
| 月次継続患者数 | 100名以上（CRM・マイページの必要性が増す） |
| 検査パッケージ売上 | 月100件以上（検査連携の自動化が必要） |
| 処方件数 | 月150件以上（院内処方・配送の内製化検討） |

---

## 内製化候補機能

### 高優先度（Phase 3前期）

| 機能 | 現在の対応 | 内製化後 |
|---|---|---|
| 患者マイページ | なし / 既存プラットフォーム | 症状スコア・処方歴・検査結果の統合管理 |
| 予約・決済 | 既存プラットフォーム | 自前予約システム + Stripe |
| 医師管理画面 | 既存プラットフォーム | 再診サマリー・症状推移グラフ |
| メール/LINE CRM | 外部サービス（SendGrid/LINE API） | 継続（引き続き外部APIを使用） |

### 中優先度（Phase 3中期）

| 機能 | 内製化の内容 |
|---|---|
| 検査連携 | 検査会社APIとの連携、結果をマイページに自動反映 |
| 薬局API | 院外薬局との処方データ連携 |
| 院内処方・配送 | 売れ筋薬剤の在庫管理＋配送オペレーション |

### 低優先度（Phase 3後期以降）

| 機能 | 備考 |
|---|---|
| ビデオ診療 | 規制・安定性の観点から引き続き既存サービス活用を検討 |
| 電子カルテ | 保険診療は既存一択。自由診療専用には簡易カルテを自作も可 |
| 電子処方箋 | 医療機関コードとの連携が必要。Phase 3後期まで不要 |

---

## 技術スタック候補

> 確定ではなく、Phase 2後期に改めて選定する。

| レイヤー | 候補 | 備考 |
|---|---|---|
| フロントエンド | Astro（現状） / Next.js | SEOはAstro、マイページはNext.jsが向いている可能性 |
| バックエンドAPI | Node.js（Hono/Express） / Supabase | Supabaseなら初期はDB＋Authを一括で賄える |
| データベース | PostgreSQL（Supabase） | スコア履歴・患者情報 |
| 認証 | Supabase Auth / Auth0 | 患者ログイン・医師ログイン |
| 決済 | Stripe | サブスク・都度課金ともに対応 |
| メール | SendGrid / AWS SES | 継続 |
| LINE | LINE Messaging API | 継続 |
| ホスティング | Vercel / AWS | 規模次第で移行 |

---

## セキュリティ・法的要件

| 要件 | 内容 |
|---|---|
| 個人情報保護法 | 患者情報の取り扱い。医療情報は要配慮個人情報 |
| 電子帳簿保存法 | 電子診療録の保存要件（5年保存等） |
| 医療法 | 患者情報システムの安全管理指針に準拠 |
| ISMS / セキュリティ監査 | 規模拡大に応じて認証取得を検討 |
| ビデオ診療の暗号化 | 既存プラットフォームに依存している間は問題なし |

---

## Phase 3移行時の注意

1. 既存プラットフォームからのデータ移行計画を事前に策定する
2. 移行期間中は旧プラットフォームと新システムを並走させる
3. 患者への事前通知（マイページURL変更・ログイン方法変更）
4. 移行後もビデオ診療は既存サービスを継続利用することで開発リスクを最小化
